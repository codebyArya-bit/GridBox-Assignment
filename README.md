# GridBox — UK Day-Ahead Wind Intelligence (v2)

**Live dashboard:** https://gridbox-wind-web.vercel.app  
**FastAPI docs:** https://gridbox-wind-api.vercel.app/docs  
**Data:** solely Elexon BMRS FUELHH + WINDFOR.

## Problem and scope
The utility is purchasing electricity one day before delivery. This historical pilot covers purchasing decisions on **January 1–31, 2026**, delivering January 2–February 1. Wind generation is weather-dependent; the dashboard reconstructs only information knowable at the purchasing cutoff and measures subsequent forecast accuracy.

### Calculation methodology and no leakage
- Forecast source: **WINDFOR**, published forecasts at hourly target timestamps. For each delivery hour, take the revision with the most recent `publishTime <= decisionCutoff`.
- Actual source: **FUELHH**, `fuelType=WIND`, half-hourly observations.
- **Like-for-like comparison:** calculate the arithmetic mean of the TWO actual MW measurements at HH:00 and HH:30, then compare to the published hourly forecast MW for HH:00. Only compute when both actual readings exist. This is an explicit defensible analytical assumption for comparing a forecast hourly MW point to an hourly average, not a claim about hourly energy or procurement volume. Raw half-hourly data appears alongside the hourly mean in the audit table. No interpolation or replacement of missing data.
- Signed error = forecast MW minus hourly-mean actual MW. MAE, RMSE and bias are based only on matched hourly pairs; 24 forecast-hour coverage and 48 underlying actual half-hour coverage are reported separately.
- Default **09:50 GMT, January 2026** references Nord Pool's N2EX GB day-ahead auction gate closure: https://support.nordpoolgroup.com/support/solutions/articles/8000088463-about-the-n2ex-day-ahead-auction . The user can select a **custom HH:MM UK-local cutoff**, clearly marked hypothetical. This does NOT assert every UK auction uses that cutoff.
- The monthly view shows all 31 purchasing decisions evaluated at **fixed 09:50 UK time** in a reproducible historical Elexon snapshot. It does not change when users explore a hypothetical one-day cutoff.

## CI and deployment
The application uses two GitHub-linked Vercel projects. The frontend rewrites /api to its separate FastAPI deployment. GitHub Actions performs backend unit tests, TypeScript build, Docker smoke, real Elexon contracts, public browser smoke, and snapshot regression across desktop/mobile. Separate Firefox/WebKit runs include WCAG AA automated checks. Monthly data is generated as a committed immutable January historical artifact so the public monthly dashboard doesn't issue 62 upstream calls each time.

## Limitations / data provenance
Only wind actuals/forecasts from Elexon are considered. Consumer demand, trading prices, procurement quantities, thermal sourcing and forecasts from other providers are intentionally out of scope. Averages are analytical assumptions, not claims about wind output in MWh. Published forecasts are post-event historical retrieval constrained by their publication timestamps. In-process cache is per serverless worker (not shared Redis). Data and site may be temporarily unavailable if upstream APIs fail.
